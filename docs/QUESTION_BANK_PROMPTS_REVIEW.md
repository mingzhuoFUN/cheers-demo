# Cheers 题库提示词与生成规则审查稿

> 用途：将本文件完整发送到另一个对话，对《真心话大冒险》和《谁最可能》的题库趣味性、尺度、语言和多样性进行调优。
>
> 整理日期：2026-08-29。内容以当前仓库实际生效代码为准，不是产品设想稿。

## 1. 生成链路概览

两个游戏都使用同一组输入变量：

- `players`：2–6 位玩家，包含 `id`、昵称、性别（当前仅允许“男/女”）。
- `warmth`：0–100 的关系温度。
- `excludeTexts`：本局已经出现的题目，交给模型避免重复。
- `questionDirection`：游戏中途选择的风格方向；可以为空。

当前优先调用 DashScope 兼容接口，默认模型为 `qwen3.7-plus`，并关闭思考输出；未配置 DashScope 时才使用 OpenAI，默认模型为 `gpt-4.1-mini`。

提示词版本缓存标识目前是 `party-fun-v18`。修改提示词后应同步修改这个版本号，否则浏览器可能继续使用旧的预生成题库。

## 2. 《谁最可能》当前实际提示词

### 2.1 System Prompt

```text
你是安全、有趣的中文聚会游戏题库设计师。
```

### 2.2 User Prompt（按当前拼接顺序原样整理）

花括号中的内容是运行时变量。

```text
生成 16 道中文聚会游戏《谁最可能》题目，严格只输出 JSON；首批保留连续游玩和去重筛选所需冗余，后续题目会按需补充。
这是酒桌热场游戏，不是访谈或心理测评。每题必须一眼看懂投票点，读完两秒内能开始投票。
可自然使用‘谁最有可能’或‘谁最不可能’，根据题意选择，不规定比例；但同一批不要全部使用同一种句。
遵守‘一题一梗、一眼一票’：每题只保留一个核心行为、冲突或反差，不把两个独立情境拼在一起。
长度由梗决定，不为凑字数添加解释。多数题目写成 14–34 字；允许少量 8–18 字的短促题和少量 35–52 字的情境题，不要求精确比例。固定开头后的核心内容至少 6 字。
只有场景条件会改变玩家的投票判断时才允许写长；删除某个条件后若投票对象基本不会改变，就删除该条件。短题也必须包含具体行为或明确反差，不能只剩抽象性格词。tag 保持简短。
每题必须做到投票点清晰，并在画面、反差、多人可投、投后有戏四项中至少做到两项；不要为了全部满足而堆叠分句。
自由选择题材，不使用封闭主题清单；提示词列举的机制只作启发，不要求逐项覆盖。
拒绝正确但无聊的正向判断，例如‘最靠谱、最会照顾人、最有仪式感、最容易交朋友、最会做攻略’；不要像人格测试，也不要把普通优点包装成问题。
允许不完美、轻微冒犯感、善意互损、暧昧试探和可辩解的社死；避免答案过于明显或只有一个玩家符合。
题目由全员同时投票，不要指定某位玩家，不要在题目中出现玩家姓名、ID或性别。
允许善意互损、暧昧试探、酒后反差和轻微社死；不得羞辱、歧视、鼓励危险行为、强迫饮酒或身体接触。
关系温度：{warmth}/100；风格坐标：{profile JSON}。坐标只控制尺度和语气，不限制题材。
{最高温度增强指令或普通温度约束}
{本批风格方向；未选择时为“本批没有额外风格方向，保持多样随机。”}
玩家构成：{count、genderCounts、composition JSON}。性别只用于判断话题适配和关系张力；混合局也不得默认异性恋，单一性别局也不要自动回避暧昧题；禁止性别刻板印象。
以下是本局已经出现的原题。禁止生成同义改写、相同情境或相同笑点，只换主语和措辞也算重复：{excludeTexts JSON}。
```

### 2.3 关系温度量化

| 温度 | 阶段 | 大胆 | 暧昧 | 暴露 | 隐私 | 搞笑 |
|---|---|---:|---:|---:|---:|---:|
| 0–24 | 破冰热场 | 3 | 1 | 2 | 1 | 8 |
| 25–49 | 熟人互损 | 5 | 3 | 5 | 3 | 9 |
| 50–74 | 暧昧升温 | 7 | 7 | 6 | 6 | 8 |
| 75–100 | 成人夜场 | 10 | 10 | 9 | 9 | 7 |

最高档会额外加入：

```text
当前是最高尺度的成年人酒局。可以直接涉及身体吸引力、想和谁约会或接吻、暗恋暴露、前任、欲望、暧昧对象、酒后冲动和关系选择；不要用含蓄的正向夸奖替代这些张力。允许尖锐和让人脸红，但不羞辱、不曝光创伤、不鼓励危险或非自愿行为。
```

其他温度加入：

```text
按风格坐标控制尺度，不要擅自升级到更高隐私级别。
```

### 2.4 中途风格方向

- `funny`：爆笑离谱——增加反差、社死、误会和现场起哄感。
- `flirty`：暧昧升温——增加心动、吃醋、吸引力和关系试探。
- `bold`：大胆坦白——更直接、更尖锐、更容易让人脸红，但仍尊重边界。
- `roast`：互损揭短——增加熟人黑历史、嘴硬和可辩解的小缺点，不做人身攻击。
- `absurd`：脑洞失控——增加荒诞假设、意外后果和不按常理的选择。
- `confessions`：酒后真话——增加没说出口的话、冲动决定和隐藏想法。
- `details`：细节侦探——熟人才能发现的小动作、习惯、微表情和藏不住的反应。
- `friendship`：损友默契——朋友间的接梗、包庇、拆台、救场和心照不宣。
- `crisis`：阵营危机——共同困境中的带队、叛变、误判、拖后腿或意外救场。
- “保持原样”：不改变当前方向，也不会专门重生成一种风格。

实际追加格式：

```text
本批风格方向：{方向说明}。方向改变题目的表达重心，但不得突破当前关系温度的尺度。
```

### 2.5 输出结构

模型需要返回 16–20 个对象，服务端最后最多保留 16 个：

```json
{
  "questions": [
    {
      "id": "字符串",
      "text": "以谁最有可能或谁最不可能开头的题目",
      "tag": "2–16 字的简短印象标签"
    }
  ]
}
```

### 2.6 模型输出后的硬校验

- 题面硬限制：8–52 个字符；固定开头后的语义核心至少 6 个字符；tag 长度：2–16 个字符。
- 必须以“谁最有可能”或“谁最不可能”开头，不固定两者比例。
- 直接拒绝包含这些“正确但无聊”表达的题：`最靠谱`、`最会照顾`、`最有仪式感`、`最容易交朋友`、`最会做攻略`、`最值得信赖`。
- 直接拒绝包含这些内容的题：色情、裸、强吻、灌酒、霸凌、羞辱、违法、自残、疾病、收入、身材、最丑、最穷。

### 2.7 去重范围和算法

- 浏览器在同一局内保存 `usedQuestionTexts`，补题时将最近最多 100 道传给 API。
- API 输入也限制 `excludeTexts` 最多 100 道。
- 同一批生成结果会彼此比较，也会与传入历史比较。
- 先去掉“谁最有可能/谁最不可能”开头和部分常见追问词，再比较语义核心。
- 完全相同、长串互相包含，或字符二元组重合率达到 `0.56`，都会判为相似题。
- 浏览器端使用相同的 `0.56` 规则再过滤一次。
- 该历史只存在当前页面内；刷新网页后会清空，不是跨局、跨刷新持久去重。

### 2.8 AI 失败时的本地备用题库

备用题库按四个温度档各有 8 道固定题。它们会随机打乱，但内容本身固定。只要 AI 请求失败、结果解析失败、校验后没有可用题，玩家就可能频繁看到这些题。这是“题库像化石”或刷新后仍感到相似的重要排查点。

备用题实际位于：`lib/who-most-likely.ts` 的 `templateBanks`。

## 3. 《真心话大冒险》当前实际提示词

### 3.1 DashScope System Prompt

```text
你是中文派对游戏题库设计师。必须只输出合法 JSON。
```

OpenAI 分支将下面的主要规则整体放进 `instructions`，语义相同。

### 3.2 主提示词（按当前拼接顺序原样整理）

```text
生成中文酒桌版真心话大冒险题库，只输出 JSON。题目要清楚、有画面、现场可执行，不写成生硬问卷。
遵守‘一题一体验’：每题只有一个核心秘密、选择或挑战；允许添加一个真正改变回答或玩法的戏剧条件，不拼接两个独立任务。
长度由体验决定，不为凑字数添加解释。真心话多数 16–38 字、最多 64 字；大冒险多数 18–48 字、最多 80 字。推荐区间用于保持节奏，不要求机械凑字数。
真心话采用‘一问一钩子’：只问一个核心信息，可以用一个具体情境或二选一制造张力；不要连续换一种说法追问。理由本身是答案核心时可以询问理由。
大冒险采用‘核心任务+可选戏剧条件’：明确做什么、对谁、怎样算完成；戏剧条件应制造表演、选择、误会或悬念。不要在完成动作后追加复盘。
输出前做删减测试；压缩不能牺牲画面感、表演性和完成条件。
本局已出现原题：{excludeTexts JSON}。不得生成相同动作、相同问题、相同互动机制或同义改写；仅更换玩家ID也算重复。
开头用 {{player:actorPlayerId}} 点名一次，之后可用“你”；目标玩家必须写 {{player:数字ID}}。禁止含糊的人物代词。
自由选择题材，风格坐标只控制尺度，不限制主题；同批题目必须使用不同场景、冲突和笑点机制，避免同义改写。
{玩家 ID、性别与组合规则}
首批为每位 actor 生成 4 道 truth 和 4 道 dare：1 道正常展示、2 道供连续换题、1 道作为校验和去重损耗冗余。后续批次由客户端按实时库存缺口提交 `inventoryNeeds`，只生成指定 actor、mode 和 count，不再重复生成整桌题库。
本局关系尺度：{关系温度说明}。每一道题都必须明显符合这一档，而不是生成通用题。关系温度不表示身体接触许可。
{当前题目走向；未选择时为“当前没有额外题目走向，使用基础风格。”}
```

### 3.3 玩家 ID、性别与组合规则

```text
玩家ID与性别映射（唯一可信来源）：{playerGenderMap JSON}。性别人数：{genderCounts JSON}。
必须先根据 actorPlayerId 和 targetPlayerIds 查询上述映射，再设计题目；禁止根据昵称猜测性别。
尤其是大冒险，要结合实际人数及参与者的性别组合调整表达和动作设计，同性与异性组合都要自然且分布均衡。
当本桌同时存在同性和异性组合时，每位 actor 的题目尽量覆盖两类目标组合；性别只影响情境适配，不得默认异性恋或套用性别刻板印象。
性别映射用于题目语境和参与者组合设计；不得根据昵称推断或改写任何玩家 ID。
```

### 3.4 关系温度量化

```text
0–24 破冰：大胆度2/10、暧昧度1/10、隐私度1/10、搞笑度8/10；轻松习惯、无厘头选择和低压力小动作，禁止感情与秘密。

25–49 熟悉：大胆度5/10、暧昧度3/10、隐私度3/10、搞笑度8/10；熟人反差、共同经历、善意互损和轻微社死。

50–74 深入：大胆度7/10、暧昧度7/10、隐私度6/10、搞笑度6/10；心动、吃醋、关系变化、没说出口的欣赏和有张力的互动。

75–100 成人夜场：大胆度10/10、暧昧度10/10、隐私度9/10、搞笑度6/10；允许直接谈身体吸引力、接吻意愿、约会选择、暗恋、前任、欲望、酒后冲动和关系试探。真心话可以让人脸红，大冒险可以有挑逗性表达、近距离互动和暧昧表演；任何真实身体接触必须明确可拒绝，并提供不接触的替代动作。
```

### 3.5 中途风格方向

- `flirty`：暧昧升温——欣赏、心动、在意和轻微关系试探。
- `heartfelt`：更加走心——真实感受、理解、支持和未表达的话。
- `exciting`：刺激一点——更直接、更有张力，但不得危险、强迫或越界。
- `funny`：轻松搞笑——反差、趣事、尴尬瞬间和善意玩笑。
- `past`：聊聊过去——第一印象、成长经历和共同回忆。
- `future`：聊聊未来——期待、理想生活和想共同完成的事情。
- `unspoken`：没说出口——一直想问或想表达但尚未说出口的内容。
- `appreciation`：彼此欣赏——具体优点、被打动的细节和感谢。
- `values`：价值观——选择、原则、生活态度和关系观念。
- `imagination`：脑洞假设——使用有趣的假设情境了解彼此。
- `chemistry`：默契挑战——通过同步选择、猜测、接话和彼此预判测试默契。
- `improv`：即兴演技——模仿、配音、角色扮演、临场台词和可观看的表演。
- `secretMission`：秘密任务——隐藏意图、不能提前解释的小任务和猜目的互动。

### 3.6 输出结构

```json
{
  "questions": [
    {
      "id": "字符串",
      "mode": "truth 或 dare",
      "actorPlayerId": 1,
      "targetPlayerIds": [2],
      "text": "{{player:1}}，……{{player:2}}……"
    }
  ]
}
```

首批目标是每位 actor 各 2 道真心话、2 道大冒险，因此人数越多，一次请求要求的题量越大。

### 3.7 模型输出后的硬校验

- 题面替换玩家占位符后至少 6 字；真心话最多 64 字，大冒险最多 80 字。
- 禁止模糊人物指代：我、他、她、它、对方、某人、在场的人；允许“你”指向开头已点名的 actor。
- 大冒险如果在动作后追加“为什么选择、解释原因、希望对方理解”等复盘，直接拒绝。
- actor 和 targets 必须都是真实玩家 ID；目标不能包含 actor；目标 ID 不得重复。
- actor 的占位符在题面中必须恰好出现一次，每一个 target 都必须在题面出现。

### 3.8 去重算法

- 去掉玩家 ID 差异和部分高频虚词后构造语义核心，因此只换玩家通常仍会判为重复。
- 完全相同、较长文本互相包含，或字符二元组重合率达到 `0.60`，判为相似题。
- 服务端会同时比较本局历史和同一批题目。

### 3.9 AI 失败时的本地备用题库

真心话和大冒险各有 8 个固定模板，再按关系温度、玩家性别组合和 actor/target 轮换选择。模板实际位于 `lib/questions.ts` 的 `truthTemplates` 与 `dareTemplates`。

备用题会随机打乱顺序，但模板数量有限。如果线上实际大量落入 `source: "fallback"`，会明显产生重复、保守、像旧题库的感觉。

## 4. 当前最值得审查的矛盾点

这些不是修改建议，而是帮助新对话快速定位题库问题：

1. 《谁最可能》同时要求“短、准、有梗”和“长短自然变化、包含中长题”，模型可能在两种目标间摇摆。
2. “趣味性硬标准”一次要求场面、反差、多人可投、可起哄四个维度，可能诱发语义堆叠和套路化。
3. 虽然声明“不使用固定主题清单”，后面仍列举七类喜剧机制；模型可能把示例误当成封闭清单。
4. 《谁最可能》最高档尺度很高，但硬校验同时屏蔽“裸、强吻、身材”等词；这是必要边界，但可能让模型整体过度收缩。
5. 两个游戏的温度档位概念接近但量化不完全一致，例如《谁最可能》破冰大胆度为 3，《真心话大冒险》为 2。
6. 《真心话大冒险》的“最小充分语义”和多条压缩规则很强，可能把题目压成机械指令，削弱戏剧性。
7. 当前性别只有二元选项；提示词虽禁止刻板印象和异性恋预设，但性别变量仍可能对实际生成贡献不足或产生模板偏差。
8. 重复历史只覆盖当前页面的一局，刷新后清空；因此模型无法知道上一局或上一次刷新展示过什么。
9. 备用题库内容固定。模型调用不稳定时，继续调提示词不会改善玩家看到的备用题，需要先观察 API 的 `source`。
